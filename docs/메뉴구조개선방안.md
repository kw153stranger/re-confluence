# Confluence 메뉴 구조 개선 방안 검토

> 현재 임베딩 중심 Cluster 방식의 한계를 진단하고, **Metadata + 기존 Path + Ontology 중심,
> Embedding 보조** 방식으로의 전환을 제안한다. 핵심 메커니즘은 코드에 반영되어 있다(맨 아래 "구현 반영 현황").

## 배경

기존 Confluence 문서를 재구성하기 위해 아래와 같은 작업을 수행하였다.

1. 페이지 단위로 LLM을 이용하여 메타정보 생성
2. 페이지 단위로 Text Embedding(TEI) 생성
3. Embedding 기반 Cluster를 생성하여 메뉴 구조 재구성

그러나 실제 결과는 기대했던 수준의 의미 있는 메뉴 구조가 생성되지 않았다.

---

## 문제점 분석

현재 Pipeline은 다음과 같다.

```
Page
 ├─ LLM → Metadata
 ├─ Embedding
 └─ Clustering
        ↓
   Menu Structure
```

이 방식은 **문서 내용(Content)** 만을 기준으로 그룹핑하기 때문에 다음과 같은 문제가 발생한다.

- 운영자의 메뉴 설계 의도가 반영되지 않는다.
- 서로 다른 목적의 문서가 내용이 비슷하다는 이유만으로 같은 Cluster로 묶인다.
- 기존 Confluence 구조를 활용하지 못한다.
- LLM이 생성한 Metadata 역시 자유도가 높아 일관성이 떨어진다.

예를 들어,

```
Infrastructure
 ├── Server
 │     └── Dell 구축
 └── Storage
       └── Dell Storage 운영
```

Embedding 기준에서는 두 문서가 매우 유사하지만, 실제 관리 관점에서는 **Server**와 **Storage**는
전혀 다른 메뉴에 위치해야 한다. 즉, **Embedding만으로는 메뉴 구조를 만들기 어렵다.**

---

## 개선 방향

Embedding 중심이 아니라

> **Metadata 중심 + Path 정보 활용 + Embedding 보조**

방식으로 변경하는 것을 추천한다.

```
Page
  → LLM Metadata 생성
  → Dictionary Normalization
  → 기존 Path Feature 추가
  → Candidate Menu 생성
  → Embedding으로 세부 위치 보정
  → 최종 Menu 추천
```

---

## 1. 기존 Menu Path 활용

기존 Confluence 메뉴는 운영자의 의도가 반영된 정보이다. Path(ancestors)를 Feature로 활용하고,
LLM 입력에도 `Current Path`로 제공한다.

```
Current Path: DC > Infrastructure > Server
```

이를 통해 "기존 Server 영역 유지 / Network·Storage로 이동 불필요" 같은 판단이 가능하다.

## 2. Metadata Dictionary 구축

LLM이 자유롭게 Metadata를 생성하지 않고 **사전에서만 선택**하도록 한다.

- **Menu Type**: Guide, Runbook, Architecture, Reference, Template, Operation, Troubleshooting, Meeting, Project, Standard, Policy, FAQ, Release
- **Technology**: VMware, OpenShift, Kubernetes, Linux, Oracle, Storage, Backup …
- **Lifecycle**: Planning, Build, Operation, Migration, Retire
- **Domain/Organization**: Infrastructure, Cloud, Database, Security, Network, Platform

## 3. Label Dictionary 구축

Label도 자유 생성하지 않는다. (`VMWare/VMWARE/vmware/VMware8` → `vmware`) 화이트리스트에서만 선택·표준화한다.

## 4. Candidate Menu 생성

`Current Path + Metadata + Embedding`을 입력으로 후보 메뉴를 만든다.

```
Metadata: Technology=NetApp, MenuType=Guide, Lifecycle=Operation
→ Infrastructure > Storage > Operation Guide > NetApp
```

## 5. Embedding 역할 변경

```
Metadata → Candidate Menu → Embedding Similarity → 최종 위치 결정
```

Embedding은 "어떤 메뉴인지"가 아니라 **"같은 메뉴 안에서 어떤 위치에 둘지"** 결정하는 보조 수단이다.

---

## Ontology 기반 구조 추천

```
Domain
 ├── Infrastructure ── Server / Storage / Network / Backup
 ├── Platform ── VMware / OpenShift / Kubernetes
 └── Database
```

문서는 독립적인 분류 축을 가진다.

| 분류 | 예시 |
|------|------|
| Domain | Infrastructure |
| Technology | VMware |
| Product | ESXi |
| Document Type | Runbook |
| Lifecycle | Operation |
| Audience | Operator |
| Tags | vmware, cluster |

## 추천 Scoring 방식

```
Final Score
= 0.35 × Ontology Match
+ 0.25 × Existing Path Similarity
+ 0.20 × Metadata Match
+ 0.20 × Embedding Similarity
```

## 최종 추천 Architecture

```
        Existing Path → Path Feature
                              │
Page ─► Metadata ─► Ontology ─► Candidate Menu ─► Embedding Similarity ─► Final Menu
   └──► Embedding ──────────────┘
```

---

## 결론

1. 기존 Menu Path를 중요한 Feature로 활용한다.
2. Metadata Dictionary를 구축하여 일관성을 확보한다.
3. Label Dictionary를 관리하여 표준화를 수행한다.
4. Ontology 기반으로 Candidate Menu를 생성한다.
5. Embedding은 최종 위치를 결정하는 보조 수단으로 활용한다.

이 방식은 기존 Confluence의 운영 의도를 유지하면서도 LLM과 Embedding의 장점을 함께 활용하는
현실적인 구조 개선 방안이다.

## 구현 반영 현황 (코드)

이 제안의 핵심 메커니즘을 코드에 반영했다. (`pytest`로 검증)

| 제안 | 구현 | 위치 |
| --- | --- | --- |
| ① 기존 Path Feature | ✅ Export가 ancestors를 `RawDoc.path`로 저장, Analyze 프롬프트에 `Current Path` 제공 | `export.py`, `prompts.py` |
| ② Metadata Dictionary(강제 선택) | ✅ Domain/Technology/MenuType/Lifecycle 사전 + LLM 출력 스냅 | `dictionaries.py`, `prompts.py`, `analyze.py` |
| ③ Label Dictionary(화이트리스트) | ✅ `snap_label` 표준화(소문자) | `dictionaries.py` |
| ④ Ontology + Candidate Menu | ✅ 도메인→기술 온톨로지 + 후보 메뉴 생성 | `menu.py` |
| ⑤ 가중 Scoring(0.35/0.25/0.20/0.20) | ✅ Ontology·Path·Metadata·Embedding 가중 스코어 | `menu.py` |
| Embedding = 위치 보정 | ✅ `score(..., embedding_sim)` 보조 항(0.20)으로만 반영 | `menu.py` |
| 추천 메뉴 경로 산출 | ✅ `menu.recommend` → `AnalysisResult.menu_path` | `analyze.py` |

**동작 예시** (Analyze 결과):
```
Current Path : DC > Platform > VMware
LLM 원출력   : domain=platform, technology=vmware, menu_type=guied, lifecycle=operation
사전 스냅    : Platform / VMware / Guide / Operation
menu_path    : ["Platform", "VMware", "Operation Guide"]
```

### 아직 남은 것(후속)
- **Build/Upload가 `menu_path`로 페이지 트리를 구성**하도록 전환 (현재 IA는 업무→연도 유지;
  메뉴 경로 기반 트리로 전환은 별도 결정 필요 — 기획서 §5·구현설계 §6.4/§6.6 개정 동반).
- Cluster의 임베딩을 **후보 메뉴 내 세부 위치 정렬**에 연결(현재 `menu.score`의 `embedding_sim` 인자만 준비).
- Product/Audience 등 추가 분류 축, Ontology 확장.
