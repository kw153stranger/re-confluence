## 1. 개요 (Overview)

기존 Confluence 공간은 시간이 지나며 문서가 산발적으로 누적되어, **동일 업무가 연도·작성자별로
흩어지고 중복 문서가 늘어나는** 문제가 있다. 필요한 문서를 찾는 데 시간이 오래 걸리고,
어떤 문서가 최신·정본(canonical)인지 판단하기 어렵다.

본 프로젝트는 Confluence 문서를 **MCP(mcp-atlassian)** 로 수집하고 **로컬 LLM(Qwen3-30B-A3B)** 으로
분석하여, **업무 중심 정보구조(IA, Information Architecture)** 로 재구성한 뒤 Confluence 신규 공간에
반영하는 것을 목표로 한다.

### 핵심 가치 (Key Value)

1. **탐색 시간 단축** — 흩어진 문서를 `업무 → 연도` 구조로 정리해 원하는 문서에 빠르게 도달한다.
2. **라벨·메타데이터 표준화** — Page Properties Report / Content by Label 기반 **자동 조회**를 가능하게 한다.
3. **사내 문서 비유출** — 로컬 LLM을 사용해 문서를 외부 API로 보내지 않고 분석한다.

## 2. 목표 및 범위 (Goals & Scope)

### 목표 (Goals)

- Confluence 페이지·첨부파일 자동 수집 (via MCP)
- Markdown 기반 로컬 저장 (Obsidian Vault)
- AI 기반 분류(업무/프로젝트/시스템/연·월) 및 라벨 추천
- 업무 중심 IA 자동 생성
- 신규 Confluence 공간 생성 및 업로드
- 업무별·연도별 조회 지원

### 범위 제외 (Non-goals)

- **원본 Space 삭제 또는 파괴적 변경** — 원본은 읽기 전용(read-only)으로 보존한다.
- **권한(ACL)·워크플로우 자동 이관** — 초기 버전에서는 수동 설정한다.
- **실시간 양방향 동기화** — 초기 버전은 배치(batch) 기반 단방향(one-way)이다.

## 3. 전체 아키텍처 (Architecture)

```
Confluence (원본, 읽기 전용)
        │  mcp-atlassian
        ▼
 [Export]   ── Raw Markdown 저장 (Obsidian Vault)
        ▼
 [Analyze]  ── Qwen3-30B-A3B: 업무/프로젝트/시스템/연월/라벨/요약/관련문서 추출 (JSON)
        ▼
 [Cluster]  ── 동일 업무 병합, 연도별 그룹핑, 중복 탐지
        ▼
 [Build]    ── 업무 중심 Page Tree · Summary · Page Properties · Labels 생성
        ▼
 [Review]   ── 사람 검수 (분류 결과 확인·수정)
        ▼
 [Upload]   ── 신규 Confluence Space 생성 및 업로드
```

### 설계 원칙 (Principles)

- **단계 독립 실행** — 각 단계(Export/Analyze/Cluster/Build/Review/Upload)는 개별 실행 가능하다.
- **중간 산출물 파일 보존** — 각 단계의 산출물(Markdown/JSON)을 파일로 남겨 **재현·재실행**을 보장한다.
- **멱등성(idempotency)** — 같은 입력에 대해 같은 결과를 만들고, 재실행 시 중복 생성하지 않는다.
- **사람 검수 게이트(human gate)** — Upload 이전 Review 승인 없이는 신규 공간에 반영하지 않는다.

## 4. 단계별 상세 설계 (Detailed Design)

### 4.1 Export — 수집

- **입력**: 원본 Space key, 페이지 범위(전체 또는 라벨/기간 필터)
- **처리**: `mcp-atlassian` 으로 페이지 본문(storage/HTML)·첨부파일·메타(작성자, 생성/수정일, 기존 라벨, 부모)를 수집하고 Markdown으로 변환한다.
- **저장 규칙 (Obsidian Vault)**

  ```
  vault/
    raw/
      <원본페이지ID>__<slug>.md      # 본문 + YAML frontmatter
      attachments/<원본페이지ID>/*   # 첨부파일 원본
  ```

- **frontmatter 예시**

  ```yaml
  ---
  source_page_id: "123456"
  source_url: "https://confluence/.../pages/123456"
  title: "2024년 상반기 구매 정산 절차"
  author: "홍길동"
  created_at: "2024-03-11"
  updated_at: "2024-06-02"
  original_labels: ["구매", "정산"]
  attachments: ["정산표.xlsx"]
  ---
  ```

- **출력**: `vault/raw/*.md` (재실행 시 `source_page_id` 기준 갱신)

### 4.2 Analyze — AI 분석

- **모델**: 로컬 Qwen3-30B-A3B (외부 전송 없음)
- **프롬프트 설계**: 시스템 프롬프트로 출력 스키마를 강제하고, 문서 본문+메타를 사용자 입력으로 전달한다.
  출력은 **엄격한 JSON 한 개**로 제한하고, 근거가 부족한 필드는 `null` + 낮은 `confidence`로 표기한다.
- **출력 JSON 스키마 (Analysis Schema)**

  ```json
  {
    "source_page_id": "123456",
    "title_normalized": "구매 정산 절차",
    "business": "구매관리",
    "project": "정산 자동화",
    "system": "ERP",
    "year": 2024,
    "month": 3,
    "labels": ["업무/구매관리", "시스템/ERP", "연도/2024"],
    "summary": "구매 정산 절차와 승인 라인을 정의한 문서.",
    "related_pages": ["123457", "120011"],
    "duplicate_of": null,
    "confidence": {
      "business": 0.92, "project": 0.71, "system": 0.88, "year": 0.99
    }
  }
  ```

- **출력 저장**: `vault/analysis/<source_page_id>.json`

### 4.3 Cluster — 병합·그룹핑·중복 탐지

- **동일 업무 병합**: `business`(+`project`) 기준으로 문서를 묶는다.
- **연도 그룹핑**: 각 업무 하위를 `year`로 그룹핑한다.
- **중복 탐지 (dedup)**: 제목 정규화 유사도 + 본문 임베딩/셋 유사도(예: cosine ≥ 0.9)로 후보를 산출하고,
  대표 문서(canonical)와 중복 후보(duplicate candidates)를 표시한다. 자동 삭제하지 않고 **검수 대상**으로 넘긴다.
- **출력**: `vault/clusters.json` (업무→연도→문서 트리 + 중복 후보 매칭)

### 4.4 Build — IA 생성

- **입력**: `clusters.json`, 각 문서 `analysis/*.json`
- **처리**: 업무 중심 **Page Tree**, 업무별 **Summary(index) 페이지**, 각 문서의 **Page Properties** 블록,
  **Labels**를 생성한다. (상세 규칙은 §5, §6)
- **출력**: `vault/build/` 하위에 업로드 대상 페이지 Markdown + 메타(JSON)

### 4.5 Review — 사람 검수

- **화면**: 파이프라인/검수 대시보드(`mockups/pipeline-dashboard.html` 참고)
- **흐름**: 문서별 추천 분류(업무/연도/라벨)를 확인하고 필요 시 수정 → **승인(approve)/반려(reject)**.
  중복 후보는 대표 문서 지정 또는 병합/제외를 선택한다.
- **승인 게이트**: 승인된 문서만 Upload 대상에 포함된다. 검수 결과는 `vault/review.json`에 반영된다.

### 4.6 Upload — 신규 공간 반영

- **처리**: 신규 Space 생성 → Page Tree 순서대로 페이지 생성 → Page Properties·Labels·Summary 반영 →
  첨부파일 업로드 → 원본 링크(back-link) 삽입.
- **멱등성/재시도**: 페이지에 `source_page_id`를 키로 저장해 재실행 시 **생성 대신 갱신**한다.
  실패 시 지수 백오프로 재시도하고, 실패 목록을 남겨 부분 재실행이 가능하게 한다.

## 5. 정보구조(IA) 설계

### 5.1 기본 트리 (업무 → 연도, 2단계)

```
신규 Space
├── 📁 구매관리 (업무 index: Summary + Page Properties Report)
│   ├── 📁 2024
│   │   ├── 구매 정산 절차
│   │   └── 발주 승인 가이드
│   └── 📁 2023
│       └── 연말 재고 실사
├── 📁 배포관리
│   ├── 📁 2024
│   └── 📁 2023
└── 📁 시스템 운영
    └── 📁 2024
```

- 각 **업무 index 페이지**는 하위 문서를 자동 집계하는 Page Properties Report와 요약을 포함한다.
- 3단계(업무→프로젝트→연도)는 문서량이 많은 업무에 한해 선택적으로 확장한다.

### 5.2 라벨 체계 (Label namespace)

| 네임스페이스 | 예시 | 용도 |
| --- | --- | --- |
| `업무/` | `업무/구매관리` | 업무 단위 조회 (Content by Label) |
| `시스템/` | `시스템/ERP` | 시스템 횡단 조회 |
| `연도/` | `연도/2024` | 연도 단위 조회 |
| `상태/` | `상태/정본`, `상태/중복후보` | 정본/중복 관리 |

### 5.3 Page Properties 표준 필드

| 필드 (field) | 예시 | 설명 |
| --- | --- | --- |
| 업무명 (business) | 구매관리 | 최상위 분류 |
| 담당 (owner) | 홍길동 | 문서 책임자 |
| 시스템 (system) | ERP | 관련 시스템 |
| 연도 (year) | 2024 | 업무 수행 연도 |
| 상태 (status) | 정본 / 중복후보 | 정본 여부 |
| 원본링크 (source) | 원본 Confluence URL | 추적성(traceability) |

## 6. 메타데이터·라벨 표준 (Metadata & Label Convention)

Page Properties Report / Content by Label 자동 조회를 위해 아래 규약을 강제한다.

- **Page Properties 매크로**: 모든 문서 페이지 상단에 §5.3 표준 필드를 포함한 Page Properties 블록을 둔다.
- **업무 index 페이지**: Page Properties **Report** 매크로로 하위 문서의 표준 필드를 표로 집계한다.
- **라벨 규칙**: 문서마다 최소 `업무/*`, `연도/*` 라벨을 부여하고, 해당 시 `시스템/*`을 추가한다.
- **정본/중복**: 대표 문서는 `상태/정본`, 중복 후보는 `상태/중복후보` 라벨로 구분해 조회·정리한다.
- **라벨 마스터(전역 목록)**: 표기 흔들림(`구매관리`/`구매 관리`/`구매팀`)에 의한 **유사중복 라벨**을 막기 위해
  전역 라벨 마스터(`labels.json`)를 두고, 문서 라벨을 정규화→유사매칭으로 **canonical 하나로 통합**한다.
  신규 라벨은 후보(candidate)로 등록해 검수에서 승인/병합한다. (상세: 구현설계 §6.4a)

이 규약이 지켜지면 "구매관리 2024 문서 목록", "ERP 관련 전체 문서" 같은 조회를 매크로만으로 구성할 수 있다.

## 7. 데이터 흐름 & 재현성 (Reproducibility)

```
vault/
├── raw/          # Export 산출물 (Markdown + frontmatter)
├── analysis/     # Analyze 산출물 (문서별 JSON)
├── embeddings/   # 문서별 임베딩 캐시 (content_hash 키, Cluster가 재사용)
├── clusters.json # Cluster 산출물 (업무→연도 트리 + 중복 후보)
├── labels.json   # 전역 라벨 마스터 (유사중복 방지, canonical/alias)
├── build/        # Build 산출물 (업로드 대상 페이지 + 메타)
├── review.json   # Review 결과 (승인/수정 내역 + 라벨 거버넌스)
└── upload.log    # Upload 결과 (성공/실패, 재실행 키)
```

- 각 단계는 **이전 단계 산출물만 입력**으로 사용하므로 특정 단계부터 재실행 가능하다.
- 예: 프롬프트를 개선했다면 `Analyze`부터, IA 규칙을 바꿨다면 `Build`부터 다시 실행한다.
- **저장 시점**: 결과는 **단계·문서 단위로 처리 완료 즉시** 저장(문서 단위 UPSERT, 집계물은 단계 말).
  순수 배치는 위 파일(vault)에 저장하고, DB 저장은 M6 웹서비스(`postgres` 백엔드)에서 활성화된다. (상세: 구현설계 §12.6)

## 8. 보안·프라이버시 (Security & Privacy)

- **로컬 LLM 사용**: 문서 본문은 로컬 Qwen3-30B-A3B로만 분석하며 외부 API로 전송하지 않는다.
- **원본 보존**: 원본 Space는 읽기 전용으로만 접근하고, 신규 Space에만 결과를 반영한다.
- **추적성**: 모든 신규 페이지는 `원본링크(source)`로 원본을 역참조해 감사(audit)를 지원한다.
- **권한**: 초기 버전은 ACL을 수동 설정하며, 민감 문서는 검수 단계에서 제외 처리할 수 있다.

## 9. 리스크 & 완화 (Risks & Mitigation)

| 리스크 | 영향 | 완화 방안 |
| --- | --- | --- |
| 오분류 (misclassification) | 잘못된 업무/연도로 배치 | `confidence` 노출 + 사람 검수 게이트 |
| 누락 (missing) | 일부 문서 미수집 | Export 카운트 대조, 실패 목록 재실행 |
| 중복 미탐지 | 중복 문서 잔존 | 유사도 임계값 튜닝 + 검수에서 병합 결정 |
| 업로드 실패 | 부분 반영 | 멱등 키 + 지수 백오프 재시도 + 부분 재실행 |
| 민감정보 노출 | 권한 오이관 | 초기 수동 ACL, 검수 제외 처리 |

## 10. 로드맵 / 마일스톤 (Roadmap)

| 단계 | 범위 | 산출물 |
| --- | --- | --- |
| **M1 — 기획·목업** (현재) | 기획서 확정, IA·화면 목업 | `docs/기획서.md`, `mockups/*` |
| **M2 — 파이프라인 PoC** | Export→Analyze→Cluster CLI, 샘플 Space | 중간 산출물 JSON/MD |
| **M3 — Build·Review** | IA 생성 + 검수 대시보드 | Build 산출물, 검수 UI |
| **M4 — Upload** | 신규 Space 반영, 멱등 업로드 | 신규 Confluence Space |
| **M5 — 하드닝** | 성능·배치 재수집·운영 문서 | Runbook, 성능 개선 |
| **M6 — 웹서비스 + 벡터DB** | 파이프라인 코어 재사용 + FastAPI 웹서비스(검수·의미검색) + pgvector | 웹앱, 벡터DB, 잡 오케스트레이션 |
| **향후** | ACL·워크플로우 이관, (검토) 동기화 | — |

> **M6 방향(하이브리드)**: 6단계 파이프라인 코어(`src/reconf`)는 라이브러리로 유지(재현성·멱등성),
> 그 위에 웹서비스 계층을 얹어 ① 검수 UI ② 파이프라인 대시보드 ③ **의미 검색**을 제공한다.
> 임베딩은 파일 캐시 대신(또는 병행) **pgvector**로 저장해 ANN 검색을 지원한다.
> 사내 문서 비유출을 위해 **사내망 셀프호스트**를 전제로 한다. 상세: 구현설계 §12.
